# bHaptics VRChat Avatar Package v3

Guidance for AI coding agents (and humans) working in this repository.

## Overview
bHaptics Avatar (`com.bhaptics.vrchat-avatar`) is a VPM package that adds bHaptics haptic devices
to VRChat avatars: it places contact receivers on the avatar, and the bHaptics Player turns their
values into vibration. This repository holds **v3**, a **full rewrite** of the v2 package
([bhaptics/VRChatOSC](https://github.com/bhaptics/VRChatOSC)), not a refactor. v3 owes v2 nothing
but the OSC contract below. It is in early development.

## Repository layout
- `Packages/com.bhaptics.vrchat-avatar/` — the package, and the only thing that ships. Edit here:
  `Runtime/`, `Editor/`, and `Tests/Editor/Contract/` (the contract reference).
- `Assets/` — local scratch, mostly untracked (test avatars are licensed). Dev-only content (test
  scenes, dev tools) goes in `Assets/_/`, apart from the package. `.gitignore` tracks only the
  paths it lists; add a `!` line to track more. `UserSettings/` is not tracked.
- `.github/workflows/`, `Website/` — release and VPM listing, from
  `vrchat-community/template-package`. The workflows read the package name from the
  `PACKAGE_NAME` repository variable.

## Development setup
- Unity 2022.3.22f1; manage packages with VCC or ALCOM.
- Depends on VRChat SDK - Avatars (`com.vrchat.avatars` `>=3.10.0`).
- Animator generation uses **Animator As Code 1.x** from hai-vr's VPM listing
  (`https://hai-vr.github.io/vpm-listing/index.json`), not the legacy `V1-2022-04` tag v2 uses.
  Users add that listing themselves, so code that uses AAC lives in its own editor assembly that
  compiles only when AAC is installed; the inspector keeps working without it, warns, and guides
  the user to add the listing. AAC is not a dependency yet; add it to `package.json` and that
  assembly when code first needs it.
- Call out any change to `package.json`, `Packages/vpm-manifest.json` or `Packages/manifest.json`;
  it changes what gets installed.

## Conventions
- Package ID `com.bhaptics.vrchat-avatar`, display name "bHaptics Avatar", version `3.0.0-dev.N`
  during development.
- Assemblies follow Package Maker's naming: `com.bhaptics.vrchat-avatar` (Runtime),
  `com.bhaptics.vrchat-avatar.Editor` (editor-only), and `com.bhaptics.vrchat-avatar.Tests` once
  the first test is written. The asmdef, not the folder name, decides editor vs runtime: editor
  code and UXML/USS go under `Editor/`; an `Editor` folder inside `Runtime/` is not editor-only.
- Namespace `bHaptics.VRChatAvatar`, sub-namespaces per folder. Never end a namespace in
  `.Editor` — it shadows `UnityEditor.Editor` inside it.
- No `b` prefix on class names (v2 had one). Do not pick names that shadow Unity types:
  `Animator`, `Avatar`, `Shader`, `GUI`, `EditorGUI`, `DeviceType`. Never pattern-replace `b[A-Z]`
  when porting: `bHaptics…` and the `bOSC/` parameter prefix also match.
- Generated assets (FX copies etc.) go to `Assets/bHaptics/Generated/` in the user's project:
  never into the package folder, which VCC replaces wholesale on update, nor next to the source,
  which may sit in `Packages/` or a vendor folder. Name them
  `<source>@bHaptics_yyyyMMdd-HHmmss.<ext>` (`Avatar_FX@bHaptics_20261110-120446.controller`), a
  new name every time, with `GenerateUniqueAssetPath` as the same-second guard. When the source is
  already one of our copies, replace its `@bHaptics_…` suffix instead of adding a second one. Keep
  `.meta` GUIDs stable across versions.
- Inside the FX, layer names start with `bHaptics/`. Parameters are the contract addresses, plus
  the synced indicator Bools `bHaptics/<Device>/<n>`, which stay out of `bOSC/`. Create AAC clips
  with `NewClip(name)`, which names them `zAutogenerated/<AssetKey>__<name>_<n>`, so they can be
  told apart (`NewClip()` puts a GUID there). A copied FX still holds the previous Apply's
  embedded clips, so Apply removes ours before adding new ones.
- Code, comments, docs and commit messages are in English. Comments are one or two lines: the
  constraint or the gotcha.

## The OSC contract (version 2)
The bHaptics Player is the consumer: it reads the avatar's parameters over VRChat's OSC. The
contract below must not change; everything else (classes, UI, prefabs, FX layers, indicator look,
receiver count and shape) is free to change.

Package version and contract version are separate. Package v3 keeps the **v2 contract** — the
`v2`/`v2m` in the addresses below is the contract version. Do not change the contract from this
repository; any change gets its own contract version (v2.1 and so on), agreed with the Player side.

1. **Addresses:** `bOSC/v2/<Device>/<n>/self|others` on PC, `bOSC/v2m/...` on Quest. Device
   segments: `Head`, `VestFront`, `VestBack`, `ForearmL/R`, `HandL/R`, `GloveL/R`, `FootL/R`.
   Receiver parameters reach the Player without any animator declaration.
2. **One schema per avatar, enforced:** never put v2 and v2m on the same avatar; the Players
   misbehave (the Quest Player plays nothing, the PC Player doubles the vibration). The Players
   pick the schema by parameter path prefix, so keep the `bOSC/` subtree for haptic channels only,
   and never give a parameter the `bOSC_v1_` or `bHapticsOSC_` prefix (older schemas).
3. **Values:** Float 0..1; the Player vibrates that hard. Receivers must be **Proximity**.
4. **self/others:** separate so the Player can give different effects for your own touch and
   another's. Exception: the Quest vest has 10 receivers that accept both and write only `/others`.
5. **Node → body region** as in the v2.3.0 prefabs. Their positions are defaults: users may move
   receivers, so the contract fixes what each node means, not where it sits. Head is **4 nodes**
   (0–3); the PC Player interpolates for discontinued six-motor headsets.
6. **Quest:** v2m only; representative nodes (vest front 0,3,8,10,11,18 and back 2,9,16,19;
   head 0; arm 0); arms and hands share `HandL/HandR`; no feet; at most 16 contacts that are not
   Local Only on the whole avatar, or VRChat strips every contact. Quest gloves use Local Only
   receivers.
7. Animator parameters are internal (v2 declared them Bool only to drive the indicator).

The reference is `Packages/com.bhaptics.vrchat-avatar/Tests/Editor/Contract/v2.3.0-contract.json`
(+ `.md` summary): 220 receivers extracted from the package v2.3.0 prefabs, mesh-less variants
only. "v2.3.0" in that name is the package it came from, not a contract version.

## Architecture
A direction to build in small vertical slices, not a fixed design: one setup component on the
avatar (editor-only, `IEditorOnly`) holds the device list → device definitions as data → a planner
computes what to build without touching the scene → emitters write receivers, parameters and
indicator layers into a controller they are given → a destructive apply. A scripting API comes
first and the inspector (UI Toolkit) sits on top. This package stays free of Modular Avatar and
NDMF dependencies.

Rules any design has to keep:
- **References, not names.** Hold assets and scene objects by reference (object fields,
  ScriptableObjects), never by name or path: users rename, move and duplicate them. What no
  reference can hold is found by name: our FX layers by the `bHaptics/` prefix, our clips by the
  `zAutogenerated/<AssetKey>__` prefix, parameters by name. Layers are not assets, and each FX
  copy gets new sub-assets, so references into an earlier copy go stale. Animation bindings are
  paths: compute them from the referenced objects, and rebuild them when those objects move.
- **Never edit the user's originals.** Content changes (FX layers) go to a copy of the controller
  in the avatar's FX slot, the only source we look at; an avatar with no FX gets a new controller.
  Before Apply, say which asset is copied, what changes, and the copy's name and folder, and warn
  about everything Apply deletes, such as our layers the user has edited. Record every write for
  Undo; asset creation is not undoable, so Undo after Apply leaves the copy file behind.
- **Core apart from UI.** Every inspector action must be reproducible from a script, so an agent
  can run it through an editor eval. No modal dialogs in the core API (a scripted call would
  hang); confirmations belong to the UI, and plans such as the FX change list come back as data.
- **Where data lives.** What is edited live (device roots etc.) is referenced from the setup
  component; fixed package files of one kind in large numbers (meshes etc.) are catalogued in
  ScriptableObjects.
- **Prevent broken avatars.** The package is responsible for keeping v2 and v2m off the same
  avatar and the contact count within limits (contract items 2 and 6), and blocks the upload
  when either check fails. Checks count only receivers that are active and not EditorOnly.
  Avatar Optimizer's Trace and Optimize deletes receivers whose parameters nothing declares, and
  its built-in bHaptics entry lacks v2m, so the package ships an AAO Asset Description (an asset,
  not a code dependency) marking `bOSC/.*` as read by external tools.
- **Platforms.** The build target decides the schema. Each device keeps both receiver sets, PC
  (v2) and Quest (v2m), under its Offset. The other platform's set, and devices Quest does not
  build, stay inactive and tagged EditorOnly, so user edits survive a switch and the upload
  carries one schema. When the build target and the active sets disagree, the inspector shows an
  error that blocks the build, with a button that switches the sets at once; indicator layers
  for the new schema then go through Apply.
- **Write Defaults:** no WD tool here; the VRChat SDK builder already warns about mixed WD and
  WD-off empty clips. Layers we add follow the WD of the controller they go into and use no empty
  clips, so they never trigger those warnings themselves.

Lessons from v2 not to repeat: logic trapped in the inspector, state inferred from the scene, FX
copies deleted and recreated (breaks avatars sharing an FX file), editor writes to prefab
instances not recorded as overrides, silent failures (unmapped bone, mixed platforms).

- Do not commit straight to `main`. Work on a branch and merge by PR with a merge commit, so the
  per-intent commits survive.
- Split commits by intent, each revertible on its own.
